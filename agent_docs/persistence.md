# Persistence

## Boundaries

[Repository contracts](../src/persistence/repositories.rs) separate roster, game, draft, session/entry, processed-update, and atomic-confirmation storage from the [use cases](../src/persistence/use_cases.rs). The typed [reporting contract](../src/persistence/reporting.rs) adds read-only leaderboard and history results. The [D1 adapter](../src/persistence/d1/mod.rs) accepts an injected `worker::D1Database`; the pure domain and use cases do not depend on Workers. Writes at the HTTP entry point are restricted to the authorized Telegram webhook.

Persistent drafts hold a validated domain selection, numeric owner, partial amounts, revision and state. Every database read rebuilds validated identifiers, names, dates and participant selections. Session reads also run the original domain confirmation checks. Malformed records return a typed corruption error; storage failures do not become successful results.

## Schema and identities

[0001](../migrations/0001_ledger.sql) creates strict tables for players, games, drafts, draft participants, sessions, session entries and processed updates. Primary and foreign keys preserve stable identities; participant identity includes its kind and owning draft/session. Roster and guest IDs with identical text remain distinct. Guest identities and names stay in the relevant session; guests never create roster rows. Display names may repeat and do not determine uniqueness.

[0002](../migrations/0002_initial_games.sql) seeds only Mahjong and Poker with an idempotent insert. There is no roster or ledger seed. Indexes support owner/state draft lookup, roster entry lookup and deterministic session date order.

Cents are stored as signed SQLite `INTEGER`. Bindings pass their canonical decimal strings through `CAST(? AS INTEGER)` and read `CAST(amount_cents AS TEXT)`, avoiding D1's JavaScript number precision limit. Numeric owners also use canonical decimal text. The integration tests verify `i64::MIN`, `i64::MAX` and a balancing cent without rounding.

## Atomic writes and replay

Draft replacement uses an optimistic revision check inside a D1 batch. An incorrect owner, revision or state forces a constraint failure before any participant replacement. Reading each header and its participants in one batch prevents mixed snapshots.

Confirmation first checks the durable update result, then verifies owner, open state and revision and invokes the pure zero-sum confirmation rules. A single D1 batch conditionally inserts the session for that exact draft revision, inserts every validated entry, consumes and increments the draft, and writes the successful update result. The session primary key permits exactly one session per draft. A failed conditional insert causes the mandatory entries to fail foreign-key or uniqueness checks; D1 rolls back the whole batch. This relies on D1's documented [transactional batch behavior](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).

The same update key returns its original session and creation instant, including after a lost response. A key reused for a different owner/draft is rejected. Another update against a consumed draft returns `DraftConsumed`. After a failed attempt, the use case rechecks the result before classifying draft conflicts, including when another request finishes between the initial result lookup and draft read. Failures never persist a success marker. Confirmed sessions expose no update/delete API; audited correction remains Phase 6.

## Telegram workflow transactions

Phase 3 adds [0003](../migrations/0003_telegram_workflow.sql) for partial Telegram selections and replay receipts. Guided selections start before a game/date is known, so they cannot yet form a domain `DraftSession`. Their document retains catalog choices, owner, group, revision, stage, selections, and integer amounts. Reads validate stored metadata and domain values. Every step atomically compares the revision and commits its reply. Confirmation creates the validated persistent draft, reuses the Phase 2 confirmation statements, consumes the workflow, and stores both `processed_updates` and the Telegram receipt in one batch. Catalog creation also commits its receipt atomically. See [Telegram notes](telegram.md).

Phase 4 adds [0004](../migrations/0004_telegram_resilience.sql). Its strict `telegram_rate_events` table stores one verified Telegram update key, numeric owner text, and UTC epoch second per admitted request. Each D1 batch prunes expired events only when no durable Telegram receipt references the key, conditionally inserts a new key below the rolling per-owner limit, and reads admission atomically. Receipt-backed keys remain eligible for delayed replay but are excluded from the current-window count by timestamp. This is the only D1 operation retried by the Worker; confirmation and workflow writes retain their single transactional attempt plus durable replay behavior. The migration also adds capacity triggers for 24 active players and 24 games, closing concurrent creation races after the application precheck.

## Reporting queries

[Phase 5 reporting queries](../src/persistence/d1/reporting.rs) read the existing immutable session and entry tables; no schema migration or aggregate cache is required. Overall, per-game, and player totals keyset-scan matching roster contributions in deterministic batches of 100 rows. Each amount crosses the D1 JavaScript boundary as exact decimal text and is added to a checked Rust `i128` accumulator before one final checked conversion to `i64` cents. This avoids SQLite `SUM` overflow and never uses floating-point arithmetic. Starting from the roster preserves exact zeroes, while selecting only `roster_player_id` contributions keeps guests out of rankings. Inactive roster identities remain visible because historical results are not erased by picker status.

Each aggregate report first captures `MAX(sessions.rowid)` transactionally with its roster, game, or player-history page. Later contribution batches restrict reads to that boundary. Confirmed sessions and entries are immutable and application inserts receive increasing row IDs, so sessions appended during a report cannot enter later batches; a player total and its displayed history therefore share one logical snapshot. Phase 6 must preserve this append-only property or revise the boundary when audited corrections and voids are designed.

Ordinary session history reads session headers only. Guest identity and amount columns are selected only by the detail query for one validated session ID. Detail decoding rebuilds typed roster/guest identities, validates names and cents, and verifies at least two entries with a zero-cent total before presentation.

Worker memory is bounded by one 100-row contribution batch, the roster cap of 24 widened totals, and the validated output page. Paginated player and session history queries fetch at most one lookahead row beyond the validated page size, remove that row, and expose `has_more`. Page sizes are limited to 50 and page numbers to 10,000; Telegram uses 10 rows. Leaderboards sort by total descending, binary display name, and stable player ID. Player and session histories sort by `occurred_on` descending and session ID descending. These complete orderings prevent missing or repeated output rows while an underlying dataset is unchanged.

Aggregation still scans every matching contribution and makes one D1 read per 100-row batch. Database rows returned per call and Worker memory are bounded, but query work, D1 read cost, and response latency remain proportional to ledger history. An aggregate table or cache could make reads independent of history, but it would require a migration, transactional cache maintenance, rebuild/recovery rules, and Phase 6 correction semantics. That architectural expansion is intentionally deferred unless measured ledger growth justifies it and the user approves it.

## Local tests and limitations

`pnpm test:d1` runs the production Rust use cases, Telegram application boundary, and D1 adapter inside Wrangler's real local workerd runtime. Native tests cannot execute `worker::D1Database`, whose implementation calls JavaScript bindings. A separate `d1-test` feature exports test RPC functions; [the small test-only JavaScript wrapper](../tests/worker.mjs) injects the Worker environment. The normal build excludes those exports. There are no test HTTP endpoints, extra backend services or new JavaScript dependencies. Telegram tests inject a fake clock and transport; HTTP rejection tests use generic fake bindings. The isolated [reporting fixture](../tests/reporting.test.mjs) verifies exact overall/per-game totals, a 102-contribution multi-batch boundary sequence, checked widened aggregation, unchanged zero-result players, guest exclusion, exact played dates, stable pagination, a later append excluded by a captured snapshot, and detail-only guest presentation.

The harness uses Wrangler 4.150.0's `createTestHarness`, `getEnv`, `getExport` and `applyD1Migrations` APIs with ephemeral local storage. It verifies an empty schema before migrations and fails if unexpected application tables exist. Failure triggers inject errors in the real database at intermediate entry and final result writes, then tests check all rollback effects and safe retry. A separate native unit repository tests the deterministic lookup race; it is not counted as a D1 integration test.

The pinned workerd reports `2026-10-13` as its newest compatibility date and rejects the production `2026-10-14` date. Only [the test configuration](../tests/wrangler.toml) uses `2026-10-13`; the production configuration remains unchanged. Remote CI passed for the Phase 2–5 implementation commits and is recorded in the [implementation plan](implementation-plan.md). The batching remediation is locally validated but has no remote CI evidence until committed and pushed. These tests and CI do not prove remote D1 behavior, deployment configuration, live Telegram behavior, or production readiness.

`pnpm db:migrate:local` targets only the `local` configuration and local D1 storage. Local placeholder database IDs are not staging/production resources. Remote migrations remain a separately authorized operation; Worker rollback does not restore schema or data.
